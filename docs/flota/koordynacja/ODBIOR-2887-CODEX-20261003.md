## Kolejność i świeża Policy

1. W transakcji odczyt bieżącego hintu i jego identyfikatorów.
2. Unikalne konta zgłaszającego, kucharza i autora rosnąco po UUID, każde `FOR SHARE`. Jest to także ochrona prawdziwego FK `reports.reporter_id → users`; KEY SHARE nie zatrzymałby korekty używającej NO KEY UPDATE.
3. Bieżący hint `FOR UPDATE`, porównanie `cook_id`, `author_id`, `recipe_id`, `cooked_event_id` z powiązaniami, dla których zablokowano konta.
4. Świeże relacje `cook`, `author`, `recipe.author`, `cookedEvent.user`, `cookedEvent.recipe.author` i sprawdzenie ich tożsamości. Istniejąca Policy ocenia ten cel i świeżego zgłaszającego.
5. Deduplikacja oraz INSERT pod tymi samymi blokadami. Po zatwierdzeniu dotychczasowe potwierdzenie i alarm.

Wycofanie używa `ZamekPary` (konta UUID → hint UPDATE), korekta konta kucharza
NO KEY UPDATE → wykonanie NO KEY UPDATE. Wskazówka jest jedyną ścieżką nowej
blokady; nie dodano globalnego zamka ról.
