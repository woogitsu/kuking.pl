#927 — `tests/Feature/GlosMarkiOpisujeArkuszPrawdziwieTest.php:175`
parsuje `resources/css/app.css` wyrażeniem, które łapie reguły CO DRUGĄ.

PRZYCZYNA (już rozpisana w zgłoszeniu, zweryfikuj sam analizą wzorca
i próbą na kilku wariantach arkusza):
```
preg_match_all('/(?:^|[}])\s*([^{}@]+?)\s*\{([^{}]*)\}/s', $css, $reguly, PREG_SET_ORDER);
```
Kotwica `(?:^|[}])` wymaga `}` przed selektorem, ale ten `}` jest już
skonsumowany jako koniec POPRZEDNIEGO dopasowania — `preg_match_all` nie
cofa kursora, więc dopasowanie N+1 nie znajduje wymaganego `}` na
starcie i jest POMIJANE. Test łapie regułę 1, 3, 5, 7… Dodanie
NIEPARZYSTEJ liczby nowych reguł przed `.kuking-word` przesuwa parzystość
i test zaczyna sprawdzać treść zupełnie innej reguły niż zamierzona,
oblewając na kodzie, którego nikt nie ruszał.

ZMIERZ SAM PRZED POPRAWKĄ: dopisz do lokalnej kopii `app.css` (nie do
gałęzi na stałe — to eksperyment pomiarowy) jedną regułę CSS przed
`.kuking-word` i uruchom test — powinien oblać na złej regule albo
zgłosić błędny komunikat. To jest TWÓJ dowód, nie przepisuj analizy
wzorca z tego zlecenia jako gotowego pomiaru.

NAPRAW wyrażenie regularne albo sposób parsowania tak, żeby był
ODPORNY NA PARZYSTOŚĆ liczby reguł — np. podziel arkusz po `}` jako
osobny krok (np. `preg_split` po granicach reguł) zamiast wymagać `}`
jako kotwicy startowej KOLEJNEGO dopasowania, albo dopasuj każdą regułę
